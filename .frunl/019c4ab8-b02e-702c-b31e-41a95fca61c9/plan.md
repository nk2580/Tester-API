# gRPC Conversion Plan for Tester-API

## Goal
Convert the current HTTP/JSON Gin service into a gRPC-based service while preserving existing behavior (create a ping record and list all pings) and keeping SQLite/GORM persistence. The plan must be executable in a locked-down Debian container with no external tooling, no network, and no package managers.

## Current State Summary
- `main.go` uses Gin with two routes:
  - `POST /ping` to create a `Ping` record in SQLite.
  - `GET /pings` to list all `Ping` records.
- Data model: `Ping { ID uint, Message string }` with GORM.
- SQLite DB: `db/data.db`.

## Constraints & Implications
- No external tooling (no `protoc`, no Go tooling downloads, no apt/pip/npm). Generated gRPC code cannot be produced via `protoc` in this environment.
- No network access; cannot fetch dependencies not already present in `go.sum` or vendor.
- We can only edit files via the provided file tools.

## Implementation Strategy
1. **Define gRPC API contract** in a `.proto` file.
2. **Add pre-generated gRPC Go code** manually (since `protoc` is unavailable). This means checking in:
   - `ping.pb.go` (messages)
   - `ping_grpc.pb.go` (service interfaces)
   These can be authored by hand to match the standard gRPC/protobuf API or copied from a previously generated template. Because code generation is unavailable, the plan includes manual authoring with explicit interfaces.
3. **Refactor server** to a gRPC server implementation:
   - Replace Gin HTTP server with gRPC server on port `:8080` (or another port if desired).
   - Implement gRPC methods to mirror the two endpoints.
4. **Update module dependencies**:
   - Add `google.golang.org/grpc` (if not already present) to `go.mod`.
   - Ensure `google.golang.org/protobuf` is required (already indirect). Might need to promote to direct if using it.
   - Without network access, dependencies must already exist in module cache or be vendored. The plan therefore includes adding a `vendor/` directory with required packages if needed (manually populated if present in repo, otherwise the plan notes the risk).
5. **Add lightweight README update** describing gRPC usage.
6. **Optional**: Provide a small Go client example (kept in repo) for local use.

## Detailed Steps

### 1. Create Protobuf Definition
- Add `proto/ping.proto`:
  - Package `testerapi`.
  - Service `PingService` with RPCs:
    - `CreatePing(PingRequest) returns (PingResponse)`
    - `ListPings(Empty) returns (PingList)`
  - Messages:
    - `Ping { uint64 id; string message; }`
    - `PingRequest { string message; }`
    - `PingResponse { string message; }` (e.g., confirmation message)
    - `PingList { repeated Ping pings; }`
    - `Empty {}` (or use `google.protobuf.Empty` if we want standard type; but that requires importing `google/protobuf/empty.proto` and its Go package).
- Given the constraints, **prefer a custom Empty message** to avoid external imports.

### 2. Add Manual gRPC/Protobuf Go Stubs
- Create `proto/ping.pb.go` with:
  - Go structs mirroring messages.
  - Implement `proto.Message` interfaces expected by `google.golang.org/protobuf`.
  - Provide file descriptor metadata (can be minimal for runtime, but must compile).
- Create `proto/ping_grpc.pb.go` with:
  - `PingServiceServer` interface.
  - Registration function `RegisterPingServiceServer`.
  - Client interface (optional).
- **Note**: This is normally generated by `protoc`. With no generator, these files must be authored carefully. The plan will include using a simplified implementation that follows the patterns used by `protoc-gen-go`.

### 3. Refactor Application to gRPC Server
- Replace Gin usage in `main.go`:
  - Remove `github.com/gin-gonic/gin` imports and HTTP handlers.
  - Add gRPC imports: `google.golang.org/grpc`, `net`.
- Create a `server` type that implements `PingServiceServer`:
  - `CreatePing(ctx, req)`:
    - Validate `req.message` not empty (optional)
    - Persist `Ping` with GORM.
    - Return `PingResponse{Message: "Ping registered successfully!"}`.
  - `ListPings(ctx, req)`:
    - Read all `Ping` rows.
    - Map to proto `Ping` message list.
- Wire up:
  - `lis, err := net.Listen("tcp", ":8080")`
  - `grpc.NewServer()`
  - `RegisterPingServiceServer(grpcServer, &server{db: db})`
  - `grpcServer.Serve(lis)`

### 4. Update go.mod/go.sum
- Add direct dependency for gRPC: `google.golang.org/grpc`.
- Ensure `google.golang.org/protobuf` is required (already indirect but will be used explicitly by the generated-like code).
- **Risk**: Without network, `go mod tidy` can't fetch. If the environment has module cache, build may succeed; otherwise, add a `vendor/` directory.

### 5. Update README
- Document gRPC usage:
  - gRPC port and service/methods.
  - Example requests (using `grpcurl` in a normal environment) but note tooling is not available inside the container.

### 6. Optional Test/Client Stub
- Add `cmd/client/main.go` with a gRPC client showing calls to `CreatePing` and `ListPings` (non-essential).

## Validation Plan (No External Tools)
- Compile check conceptually by ensuring:
  - All imports resolve (grpc, protobuf, gorm, sqlite).
  - `main.go` references correct service registration.
  - Proto structs compile and match gRPC service interfaces.
- Since build tools are not available, rely on careful static review.

## Risks & Mitigations
- **Manual protobuf/gRPC code errors**: Mitigate by using minimal, well-known patterns and struct tags. If possible, reuse templates from existing generated code (if available in repository). There are no such files currently.
- **Missing dependencies** due to no network: Mitigate by vendoring `google.golang.org/grpc` and `google.golang.org/protobuf` if they are already in the repo or otherwise note as a build risk.
